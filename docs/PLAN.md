```

        │                                                          │
        ▼                                                          │
    КРЕСТИКИ (баланс) ── расход на нормы ─────────────────────────┘
        │
        ├──► ПОСАДКА грядки/сада (розыгрыш N карт по уровню растения)

        │    РОСТ (норма = Σ карт × кол-во растений)
        │        ▼
        │    СБОР УРОЖАЯ → РАСТЕНИЯ на СКЛАД (грядка снова «молодая»)
        │
        ├──► БИБЛИОТЕКА РЕЦЕПТОВ (изучение = вышивка нормы изучения)
        │
        ├──► ШАТЁР (стройка = розыгрыш N карт; alchemy/sewing/workshop)
        │        ▼
        │    ПЕРЕРАБОТКА растения → товар (расход растения со склада + норма)
        │        ▼
        │    ТОВАР на СКЛАД
        │
        ├──► СКОТНЫЙ ДВОР (8 животных, норма на животное, кубик 1–6 × норма продукции)

        │

        │           выполнить → списание + МОНЕТЫ)
```

## 3. ⚠️ Ключевые проектные решения

> Статусы: ✅ — рекомендация, 🔒 — подтверждено автором, ⚠️ — открытая деталь.
> Решения с 🔒 считаются принятыми и не требуют повторного согласования.

### DP-1. Каноничность источников  ✅ 🔒

Расхождения между `principe.md` и `Правила.md` (число карт в розыгрыше,
сокровища, 1 vs много растений на грядке, норма животного).

- ✅ **Решение: `principe.md` каноничен для механик; `Правила.md` — справочник
  контента** (атлас растений с именами, точные таблицы норм, маршрутный лист с
  числами, рецепты зелий, 8 животных, 5 питомцев).

### DP-2. Модель грядки (фундаментальное изменение)  ✅ 🔒

`principe.md`: грядка = **слот** — первый выбор растения закрепляется навсегда;
при посадке игрок задаёт **количество** (1–~20); норма = база × количество; сбор
урожая → стадия снова «молодое», растение то же. Сейчас: 1 клетка = 1 растение,
qty всегда 1, можно пересаживать заново, клетка освобождается при сборе.

- ✅ **Решение: модель principe.md** (слот + закрепление + количество).
  Затрагивает: `Plot`, `FieldCell`, `routes/fields.py` (plant/harvest),
  расчёт нормы, фронт `Field.tsx`. Это базис для склада растений, заказов v2, зелий.
- **Подтверждено автором:** общий склад с категориями, растение закрепляется
  за грядкой навсегда.

### DP-3. Фото-отчёт «до/после» + условие отшива  ✅ 🔒

`principe.md`: два фото (до отшива на пустом участке, после — с нашитыми
стежками) + per-растение «условие отшива» (напр. сюжет/объект), которое админ
задаёт для каждого растения и видит игрок в задании. Сейчас: 1 `photo_url`,
условие не хранится.

- ✅ **Решение: 2 фото + условие отшива per-растение.** Затрагивает:
  `StitchReport` (→ `photo_before_url`/`photo_after_url` + `context_type` +
  `context_id`), `Plant` (+ поле `stitch_condition`), `routes/stitches.py`,
  модерацию в админке.
- **Подтверждено автором:** фото до/после для ВСЕХ действий (посадка,
  переработка, животные, изучение рецептов).
- Контекст отчёта: `context_type` ∈ {`plant_grow`, `recipe_study`, `production`,
  `animal_build`, `animal_produce`, `tent_build`}, `context_id` = ID связанной
  сущности.

### DP-4. Склад растений + библиотека рецептов + переработка  ✅ 🔒

`principe.md`: урожай → **склад растений** (растения как предметы); чтобы
переработать растение в товар, нужно **изучить рецепт** в библиотеке
(вышивка нормы изучения, 3 уровня нормы, иконка `?` → картинка товара);
переработка в шатре тратит растение со склада + норму (per-уровень растения ×
количество).

- ✅ **Решение: полный цикл principe.md.** Новые сущности: `UserRecipe`,
  расширение склада на растения, поля норм изучения и норм переработки
  per-уровень в настройках.
- **Подтверждено автором:** общий склад с категориями (растения + товары).

### DP-5. Колода карт и сокровища  ✅ 🔒

`principe.md`: уровень растения 1 → 1 карта из 15 (без сокровищ); уровень 2 →
2 карты без повторов + возможны сокровища; уровень 3 → 3 карты. То же для
шатров: портниха=3, мастерская=4, зельеварение=5. Сейчас: всегда 1 случайный цвет
+ 1 случайное кол-во (1–5), без колоды, без сокровищ, без N карт.

- ✅ **Решение: внедрить колоду 15 обычных карт (3 цвета × 5 номиналов) +
  отдельные карты сокровищ (те же 3 цвета, кол-во настраивается).** Норма при
  нескольких картах = Σ норм. Розыгрыш параметризован числом карт и флагом
  «сокровища разрешены».
- **Подтверждено автором:** карты сокровищ — голубые, зелёные, фиолетовые.
  Игрок вписывает свои нормы на каждый цвет сокровища в настройках
  (диапазон 1–5000). Это усложнение: игрок сам решает, насколько большая норма.
- Нормы сокровищ хранятся в `UserCrystalNorm` с цветами `treasure_green`,
  `treasure_blue`, `treasure_violet`.

### DP-6. Уровни и маршрутный лист  ✅ 🔒

`principe.md`: переход на новый уровень при **обоих** условиях: монеты ≥ порога
И грядок ≥ порога. С уровнями открываются территории, +загоны, питомцы-помощники,
сады. 0 → 16 уровень. Админ задаёт в настройках таблицу
«уровень-монеты-грядки-что открывает». Сейчас: `User.round` — просто счётчик.

- ✅ **Решение: 4 варианта маршрутного листа в админке.** Сущность
  `LevelGate` (`variant` 1–4, `level` 1–16, `coins_required`, `plots_required`,
  `rewards` JSON). Админ создаёт/редактирует 4 варианта (Правила 7.5).
  Игрок в профиле выбирает вариант — выбор **не меняется** в дальнейшем.
- Хранение выбора: `User.route_variant` (1–4, nullable до выбора).
- Проверка перехода — после каждого `fulfill_order` (и ручной триггер).
- Награды: «+N загонов», «открыть сад уровня X», «+1 питомец» и т.д.
- **Подтверждено автором:** админ задаёт 4 варианта в админке, игрок выбирает
  в профиле, выбор не меняется.

### DP-13. Разделение round и level  ✅

Сейчас есть только `User.round`. По `principe.md` и `Правила.md` это разные
понятия: **раунд** — полный цикл от посадки до продажи/сбора; **уровень** —
этап маршрутного листа (0–16), открывающий контент.

- ✅ **Решение: разделить.** `User.round` — номер раунда, увеличивается при
  сборе урожая (завершении цикла). `User.level` — текущий этап маршрутного
  листа (0 изначально, растёт при выполнении условий LevelGate). `round`
  используется для: expiry эффектов зелий («до конца раунда»), статистики.
  `level` используется для: гейтов контента (сады, загоны, питомцы).

### DP-14. Лесная лечебница: поляна + лавка + лечебница  ✅ 🔒

> Новая ветка игры (грилл-сессия 2026-08-18). Все решения подтверждены автором.

- **Ингредиенты — новая сущность.** `Ingredient` (каталог: картинка без стадий,
  code авто) + аптекарский склад `UserIngredient`. Общий `Inventory`
  (растения/товары) не трогаем.
- **Единое время МСК для всех.** Часовой пояс игрока в профиле НЕ нужен.
  Утилита `services/msk_time.py`. Окно привязано к клетке:
  утро 04:00–10:00, день 12:00–15:00, ночь 21:00–03:00 (через полночь),
  всегда. Мёртвые зоны (03–04, 10–12, 15–21) — задуманы.
- **Лесная поляна** (`field_kind="meadow"`): клетки-добычи. Список ингредиентов
  клетки и её окно задаёт админ при разметке. Сбор: бесплатно, 1 раз в сутки
  с клетки (сброс 00:00 МСК), случайный ингредиент из списка (равновероятно).
  Вне окна клетка «спит» и сообщает время возврата. Не все ингредиенты
  размещаются на клетках — остальные добываются только через лавку.
- **Городская лавка** (`field_kind="shop"`): клетки-бартера. Статичный список
  ингредиентов на клетке задаёт админ. Обмен 1:1 по количеству, отдавать можно
  только ингредиенты аптекарского склада. Мгновенно, без вышивки.
- **Лесная лечебница** (`field_kind="infirmary"`): по локации-картинке на каждое
  животное каждого уровня (3 уровня). Клетки = части тела животного. Осмотр
  части (бесплатно, без лимита) → стабильный список проблем. Справочная
  таблица «симптомы → болезнь → мазь» — отдельный элемент локации (модалка),
  заполняет админ. Игрок выбирает диагноз: верно → карточка рецепта мази;
  неверно → игра мазь не выдаст и списывает штраф 200 крестиков; попытки не ограничены (при балансе < 200 — блок). Варка — механика,
  похожая на зельеварение (слоты), но с конкретными ингредиентами и
  количествами; мгновенная, без stitch_report.
- **Награда за лечение** — только коллекционная карточка (монет/крестиков нет).
  Вылеченное животное здорово навсегда, дублей карточек нет.
- **Прогресс уровней пациентов:** все животные уровня доступны одновременно;
  вылечил всех текущего уровня → открыт следующий. Гейтинг локаций —
  существующий `Field.min_level` (задаёт админ).
- **Ачивки** — через существующую систему достижений (первое излечение, уровень
  пройден, полная коллекция).
- **Порядок реализации:** ингредиенты+склад → поляна → лавка → лечебница →
  карточки/ачивки. Весь контент (животные, болезни, рецепты, таблица, клетки) —
  через админку, без кода.

## 5. Сквозные архитектурные принципы

1. **Все нормы — настройки.** Нормы изучения/переработки/животного/продукции
   хранятся в `settings` или per-user. Никаких хардкодов в коде.
2. **Розыгрыш карт — один сервис.** Вынести `draw_crystals(num_cards,
   allow_treasure)` в `services/card_draw.py` и вызывать из plant/build/animal.
3. **События для достижений/уровней.** Ввести пост-коммит хуки в роутах:
   `on_plant`, `on_harvest`, `on_craft`, `on_fulfill`, `on_animal_product`,
   `on_recipe_learned`, `on_potion_brewed`. Достижения и проверка уровня
   подписаны на них.
4. **Модели → миграция → роуты → тесты → фронт.** Порядок внутри фазы строго
   по AGENTS.md. Миграция после ЛЮБОГО изменения `models.py`. Тесты обязательны.
5. **Lazy-импорт моделей в `services/`.** Конвенция бэкенда — сохранять.
6. **Без комментариев** в Python без запроса; TS — без лишних типов/комментариев.
7. **`code` генерируется авто** (`_auto_code`); в тестах проверяем непустой code.
8. **Граф знаний.** После создания/удаления файлов:
   `python -m graphify --update D:/Боты/Ферма`.

### Фаза 0. Фундамент: колода карт + сокровища + модель грядки-слота + фото до/после  ✅

> Зависит от: **DP-2, DP-3, DP-5**. Базис для всех остальных фаз.
> Статус DP: DP-2 🔒, DP-3 🔒, DP-5 🔒.

**0.1. Колода карт и сервис розыгрыша (DP-5)**
- Модель `CrystalCard` (каталог: color ∈ {green,blue,violet}, value 1–5,
  is_treasure bool, image_url) либо фиксированный набор из настроек.
- Сервис `services/card_draw.py`: `draw_cards(num: int, allow_treasure: bool)
  -> list[Card]` (без повторов среди обычных; сокровища — отдельно).
- Настройки: `treasure_cards_count` (по умолчанию 3).
- Нормы сокровищ: игрок задаёт сам в `UserCrystalNorm` с цветами
  `treasure_green`, `treasure_blue`, `treasure_violet` (диапазон 1–5000).
  Это часть онбординга (рядом с обычными нормами кристаллов).
- Параметризация розыгрыша: уровень растения / тип шатра → (`num_cards`,
  `allow_treasure`).
- Тесты: детерминированный розыгрыш (mock random), без повторов, сокровища
  только когда разрешены, норма = Σ обычных + Σ сокровищ (по нормам игрока).

**0.2. Модель грядки-слота (DP-2)**
- `Plot`: `qty` уже есть (использовать), `status` расширяется
  (`planted`/`grown`), при harvest → НЕ освобождать клетку, а сбрасывать в
  «молодое» (тот же `plant_id`, `accumulated=0`, новый розыгрыш карт при
  повторной посадке количества).
- `FieldCell`: при plant — закрепить `plant_id` навсегда (запрет смены).
- При посадке: игрок выбирает растение (из разрешённых локации) + количество

### Фаза 8. Зельеварение  ✅

> Зависит от: **DP-10** 🔒, Фаз 1 (ингредиенты на складе), 5 (заказы на зелья).

- **Отдельная локация.** Стол зельеварения — отдельная страница с
  админскими клетками под: книгу рецептов, отображение рецепта, котёл
  с окошками для ингредиентов, бутылочку с готовым зельем.
- **Процесс варки (без stitch_report, мгновенно):**
  1. Игрок нажимает на книгу рецептов → выбирает 1 зелье из доступного уровня
     (на 1 уровне — 6 вариантов).
  2. Жмёт «Установить рецепт и котел» → на локации в админских клетках
     появляются: картинка рецепта + котёл с N окошками (4/5/6).
  3. Под каждым окошком — иконка нужного типа ингредиента (листик/гранат/…).
  4. Игрок нажимает на окошко → бот показывает отфильтрованный склад
     (только предметы нужного типа). Если подходящих нет: «У вас нет
     подходящего ингредиента».
  5. Игрок выбирает по 1 предмету в каждое окошко → в окошках появляются
     картинки выбранных предметов.
  6. Все окошки заполнены → кнопка «Сварить зелье».
  7. В клетке для бутылочки появляется картинка зелья.
  8. Бот: «Зелье отправлено на склад. Получен бонус: [название]».
- **Зелье на складе + бонус:**
  - Зелье попадает на склад как товар (со своим `product_id`).
  - Бонус зелья сохраняется в `UserPotion.bonus_code` до активации игроком.
  - Игрок идёт в заказы → находит карточку с заказом на это зелье → продаёт.
  - Зелье уходит со склада, но **бонус сохраняется** до нажатия «Применить бонус».
- **Котлы и прогрессия:**
  - Оловянный (4 ингр.) → доступно 6 зелий 1 уровня.
  - Серебряный (5 ингр.) → доступно 5 зелий 2 уровня (после варки всех 6 простых).
  - Золотой (6 ингр.) → доступно 4 зелья 3 уровня (после варки всех 5 средних).
  - Всего 15 зелий. Переход между котлами — достижения.
- **Заказы на зелья.** У каждого зелья 1 закреплённый заказ. Цены:
  - 1 уровень: 100 монет, 2 уровень: 150, 3 уровень: 200.
- **Ингредиенты** — 6 типов, обезличенные (в рецепте только тип).
  Берутся со склада, без повторов в одном рецепте.
  Иконки: 🟢 грядка, 🔴 сад, 🥚 скотный двор, 🔨 мастерская, 🧵 портниха, 🕐 зельеварение.
- **Модели:**
  - `PotionRecipe`: `code`, `name`, `level`, `ingredient_slots` (JSON: 4/5/6 строк-типов),
    `bonus_code` (один из 15), `image_url`, `reward_coins`.
  - `Cauldron`: `user_id`, `recipe_id`, `material`, `capacity`, `status`
    (`empty`/`filling`/`ready`).
  - `CauldronSlot`: `cauldron_id`, `slot_index`, `item_type`, `item_id` (со склада).
  - `UserPotion`: `user_id`, `potion_recipe_id`, `bonus_code`, `activated` (bool).
- **Бонусы зелий** (15 шт., единоразовые):
  - После варки зелья бонус сохраняется в `UserPotion.bonus_code`.
  - Кнопка «Применить бонус [название]» появляется если есть неактивированный бонус.
  - После применения: `UserPotion.activated = True`, бонус расходуется.
  - Список: `double_garden_harvest`, `double_orchard_harvest`,
    `double_animal_product`, `skip_plant_stitch`, `early_level_up`,
    `double_order_reward`, `free_pet`, `extra_barnyard_slot`,
    `bonus_sewing_product`, `bonus_workshop_product`, `bonus_alchemy_product`,
    `skip_animal_stitch`, `unlock_garden_l3`, `unlock_orchard_l3`, `partial_order`.
- **API:**
  - `GET /api/potion-recipes` — список рецептов зелий (доступные по уровню).
  - `POST /api/cauldrons` — установить рецепт + котёл (выбор зелья → создание котла).
  - `GET /api/cauldrons/{id}` — состояние котла (слоты).
  - `GET /api/cauldrons/{id}/slot/{n}/warehouse` — склад, отфильтрованный по типу слота.
  - `POST /api/cauldrons/{id}/slot/{n}` — положить предмет в слот.
  - `DELETE /api/cauldrons/{id}/slot/{n}` — убрать предмет из слота.
  - `POST /api/cauldrons/{id}/brew` — сварить зелье (мгновенно: списание со склада,
    +зелье на склад, +UserPotion с бонусом).
  - `GET /api/potions` — зелья с бонусами игрока.
  - `POST /api/potions/{id}/activate` — применить бонус.
  - `GET /api/admin/potion-recipes` — CRUD рецептов + бонусов.
- **Различие с шатром зельеварения:** шатёр (Фаза 1) = переработка растений в
  товары через stitch_report. Стол (Фаза 8) = мгновенная варка зелий из
  готовых ингредиентов со склада, без stitch_report.
- Тесты: выбор рецепта, заполнение слотов, фильтрация склада, варка,
  бонус сохраняется после продажи.

> Зависит от: **DP-14** 🔒. Новая ветка поверх фаз 0–10; существующие механики

- Модели: `Ingredient` (code авто, name, description, image_url, sort_order),
  `UserIngredient` (user_id, ingredient_id, qty; uq user+ingredient).
- Админка: раздел «Ингредиенты» (CRUD + картинка; поле «Код» в форме

- Тесты: CRUD + права (player 403 на админ-роуты), авто-code непустой,
  склад пуст после старта, пополнение.

**11.2. Утилита времени + Лесная поляна**
- `services/msk_time.py`: `now_msk()`, `window_active(kind)`,
  `next_open_at(kind)`; ночь 21:00–03:00 переходит через полночь.
- Поле `field_kind="meadow"`; клетки `kind="gather"` + конфиг `GatherCell`
  (field_id, col, row, window ∈ morning/day/night/always) +
  `GatherCellIngredient` (м2м — список ингредиентов клетки).
- `UserGatherLog` (user_id, cell_id, date) — лимит 1 сбор с клетки в сутки,
  сброс в 00:00 МСК.
- Роуты: `GET /api/fields/{id}` — клетки поляны отдают
  `window/available/next_open_at` (вне окна — «спит, вернитесь в HH:MM МСК»);
  `POST /api/meadow/cells/{cell_id}/gather` → случайный ингредиент из списка
  (равновероятно) на аптекарский склад; вне окна — 400 с временем возврата;
  повторный сбор за сутки — 429.
- Админка FieldEditor: тип клетки «добыча» — выбор окна + списка ингредиентов.
- Тесты: все окна и «всегда» (mock `now_msk`), ночь через полночь, 1/сутки,
  429 на повтор, случайность в пределах списка, права, пустой список клетки.

**11.3. Городская лавка (бартер)**
- Поле `field_kind="shop"`; клетки `kind="trade"` +
  `TradeCellIngredient` (закреплённый статичный список ингредиентов клетки,
  задаёт админ; ротации нет).
- Роут: `POST /api/shop/cells/{cell_id}/barter`
  `{want_ingredient_id, give_ingredient_id, qty}` — валидация: `want` в списке
  клетки, qty ≥ 1, отдаётся ровно то же qty, наличие на аптекарском складе →
  атомарный обмен одним коммитом.
- Фронт: модалка клетки лавки — «что беру (из списка клетки) + кол-во +
  что отдаю (из аптекарского склада)».
- Тесты: happy path, want вне списка клетки, нехватка на складе, qty≠qty,
  права.

**11.4. Лесная лечебница (диагностика + варка + лечение)**
- Модели:
  - `Remedy` (code, name, description, image_url) — мази/снадобья.
  - `RemedyRecipeItem` (remedy_id, ingredient_id, qty) — состав из конкретных
    ингредиентов с количествами.
  - `Disease` (code, name, description) + `DiseaseProblem` (disease_id,
    part_key, text) — проблемы по частям тела.
  - `PatientAnimal` (code, name, level 1–3, image_url, card_image_url) —
    больные животные; каждому — своя локация `field_kind="infirmary"`
    (map_url = картинка животного).
  - Клетки `kind="body_part"` + `part_key` в конфиге клетки (связь с проблемами).
  - `UserPatientState` (user_id, patient_id, status sick/healed, healed_at).
  - `UserRemedyCard` (user_id, patient_id, remedy_id) — карточка рецепта за
    верный диагноз.
  - `UserCard` (user_id, patient_id, earned_at) — коллекция.
- Справочная таблица: `GET /api/infirmary/handbook` — «симптомы → болезнь →
  мазь» (из Disease + проблем + связи болезнь→мазь); фронт — модалка-элемент
  на локации, доступна всегда.
- Роуты:
  - `GET /api/infirmary/patients` — пациенты текущего уровня + прогресс
    (вылечено N из M, доступен ли следующий уровень).
  - `POST /api/infirmary/patients/{id}/cells/{cell_id}/examine` — осмотр части
    тела → стабильный список проблем (бесплатно, без лимита, идемпотентно).
  - `POST /api/infirmary/patients/{id}/diagnose {disease_id}` — верный диагноз
    → создание `UserRemedyCard`; неверный → 400 + штраф 200 крестиков
    (`crosses_balance`); при балансе < 200 попытка блокируется.
  - `POST /api/remedy-cards/{id}/brew` — проверка наличия всех ингредиентов
    рецепта на аптекарском складе → списание → пациент излечен
    (`UserPatientState.healed`) → выдана `UserCard`. ⚠️ открытая деталь:
    мазь не хранится, варка по карточке лечит сразу (альтернатива — полка
    мазей `UserRemedy` для варки про запас), решить перед стартом 11.4.
  - `GET /api/collection` — коллекция карточек игрока (N/M, невылеченные —
    силуэт/заглушка).
- Админка: разделы «Мази» (состав = список ингредиентов с количествами),
  «Болезни» (проблемы + part_key, связь с мазью), «Пациенты» (уровень,
  картинка, карточка-награда); FieldEditor — клетки «часть тела» с part_key.
- Прогресс: все `healed` текущего уровня → пациентам следующего уровня
  открывается доступ.
- Фронт: страница «Лечебница» — список пациентов уровня (локации с клетками
  частей тела), модалка справочника, диалог выбора диагноза, экран варки
  (слоты как в зельеварении, но с конкретными ингредиентами и количествами).
- Тесты: осмотр возвращает проблемы, неверный диагноз: −200 крестиков и без
  карточки (баланс < 200 → блок), верный → карточка, повторный диагноз уже излечённого → 400, варка списывает
  ингредиенты/лечит/выдаёт карточку, дублей карточек нет, гейтинг уровней
  пациентов, права.

**11.5. Коллекция + ачивки**

## 7. Дорожная карта (порядок)

Зависимости:
- **Фаза 0** блокирует почти всё (колода, грядка, фото).
- **Фаза 1** (склад/рецепты) нужна Фазам 4, 5, 8.

```
Фаза 0 (фундамент) ──► Фаза 1 (склад+рецепты) ──┐
        │                                         ├─► Фаза 5 (заказы v2)

                              └─► Фаза 4 (животн.)┘
                                                   │
        Фаза 6 (питомцы) ◄── Фаза 2               │
        Фаза 7 (касса)    ◄── Фаза 1              │
        Фаза 8 (зелья)    ◄── Фаза 1 + 0          │
        Фаза 9 (достиж.)  ◄── все событийные      │
        Фаза 10 (полир.)  ◄── в конце
        Фаза 11 (лесная ветка) ◄── фазы 0–2 (поля, уровни, админка)
```
